# 多机器人管理：本次实现与边界

本次将统一管理入口嵌入现有 Bridge，继续使用原网址和原管理端口。原机器人固定标识为 `primary`，原页面地址、QQ 登录和 DSH 模型对话 ID 保留。**支持接入独立 worker 不等于已经上线两个真实 QQ；当前不能声称完成真实双 QQ 验收。**

实际新增实例的方法见[多机器人接入说明](MULTI_BOT_SETUP.md)。本次没有增加进程运维面板、自动安装/启动 SnowLuma、自动扫码或代理服务管理。

## 已实现的管理方式

浏览器使用统一账号登录主 Bridge。主 Bridge 中的 Manager 展示机器人列表，提供新增连接、更新、身份核验和启用；服务端 adapter 调用各 worker 的固定回环机器接口。浏览器不能获得 worker 的机器令牌，worker 不接受浏览器登录 Cookie、令牌查询参数或账号初始化。

每个 QQ 使用相同项目代码、独立运行目录、独立 Bridge、独立 SnowLuma 环境，以及独立 DSH home/端点。源码与静态页面可复用；配置、state、roles、运行锁、MCP 绑定和可写 preset 均分开。没有假定 SnowLuma 能在一个进程中同时登录两个 QQ。

| 能力 | 本次行为 |
| --- | --- |
| 账号 | 只在主入口维护一套账号，不为各 bot 复制登录系统 |
| 管理员 | 管理接入连接与各 bot 的管理接口；QQ 的 ownerQQ 仍独立配置 |
| 普通账号 | 按 botId + conversationKey 授权查看概览和费用；可管理自己的角色卡、版本，并仅应用到获授权对象 |
| 原页面 | 继续管理 primary；机器人列表与详情通过明确的 botId 选择对象 |
| 会话存档 | bot 内按对象与稳定人设身份保存；甲→乙→甲可继续原模型 ID，同人设也可保留多段历史 |
| 费用 | 各实例保留自己的 usage 账本和日报，按 bot 与对象归属，金额仍为估算 |
| 角色模板 | worker 初始角色目录为空，由管理员或获授权成员建立；不复制主 bot 的私人卡片 |

接入的“启用/停用”控制 Manager 是否代理该实例，不是启动/退出 QQ 或进程控制。已运行 worker 的实际聊天还受它自己的允许列表、模式与暂停状态约束；不要把停用管理连接当成已经停止其 QQ 服务。

## 数据隔离与 SQLite

主入口与每个 worker 在各自 state 目录中使用 SQLite。账号与会话、角色等原有文件经校验后一次性导入；旧文件留作备份，SQLite 成为已迁移文档的权威来源。角色正文保留受控文件镜像，便于兼容提示词读取。用量日志仍由各实例账本管理，不把供应商总账冒充逐机器人明细。

| 数据 | 完整归属 |
| --- | --- |
| 用户授权 | userId + botId + group/private 会话键 |
| 角色与版本 | botId + 稳定角色身份；同名不代表同一身份 |
| 模型存档 | botId + recordId，保留原 DSH sessionId 和权限策略 |
| 当前选择、未读、队列、限流 | botId + conversationKey；不同实例运行态也物理分开 |
| 智能体令牌 | 只对所属 bot 的会话有效；切换与重置撤销旧代调用 |
| 费用与内部学习任务 | 所属 bot + 会话/内部任务 + 调用记录 |

这里的 botId 是命名空间，不需要改写旧模型 ID。A、B 同在 group:456，也有独立角色、消息窗口、话题、队列、存档和费用；同号 private:456 继续是另一会话。

存储采用严格版本/字段校验、SQLite 事务和读取版本冲突检查。损坏、未来版本或不可读时拒绝写入，不自动清空或用旧 JSON 覆盖新数据。首次升级保持原账号身份、密码散列、有效登录会话、角色身份与原 DSH ID；旧普通账号的原范围仍只归 primary，不自动授权到新 bot。

## 机器路由与身份

Manager 仅连接登记过的 `http://127.0.0.1:端口`，不接受任意 URL，不跟随重定向。实例 botId、预期 QQ 和实际 QQ 必须一致，QQ/DSH 未就绪时拒绝代理；同 QQ 和同管理端口不能重复登记。

主 bot 和 worker 都可绑定 expectedQQ。身份核验同时检查 WS 与 HTTP 的 get_login_info；连接更换先撤销旧身份，旧异步探测不能复活它。HTTP 发送前再次核验，防止 WS 连 A 而 HTTP/token 配到 B。HTTP 与 WS token 分别配置，不假定它们相同。

Manager 每次重新校验浏览器身份与范围，再构造可信成员上下文。浏览器提供的 principal、Cookie 或 agent 头不被转交。受控代理拒绝账号、嵌套机器人管理、凭据轮换等命名空间；响应再次去除凭据字段。机器凭据不回显给页面，也不进入普通账号的响应。

## 默认不让两个机器人自动对聊

已登记 QQ（包括软删除或停用记录）组成已知机器人集合。新 bot 启用前同步主 bot 和所有启用 worker；任一同步失败，拒绝启用。worker 持久化集合，首次尚未同步时不处理聊天或发送，避免重启窗口绕过过滤。

过滤在消息进入未读、唤醒、黑话学习等路径前执行，覆盖普通消息与拍一拍事件；自己的消息回声同样不触发新回复。已知 bot 即使 @ 或引用另一个 bot，也不会自动开启对聊。无法可靠识别未登记的外部 AI 账号，因此不能承诺过滤所有外部机器人。

本次未开放“允许机器人互聊”。以后如需开放，必须先实现人工启动许可、指定 bot 对与群、共享回合/时间/费用预算、发送前复查和紧急停止，再设计入口；仅修改人设不足以防循环。

## 为什么第一版使用独立 DSH

独立 DSH 的常驻资源更多，但当前模式、模型默认值、preset 和 MCP 绑定有全局作用范围。只分 workspace 不能证明工具目标隔离，因此第一版用独立 home、端口与配置，减少跨 bot 设置和工具误投。

这不是操作系统安全隔离。同一 OS 用户的完整本地工具仍可能访问其他目录；closed-agent 继续保持现有管理员专用边界。不互信主体需要额外系统权限隔离，不能用不同目录代替。

资源先测再选：记录单/双实例空闲内存、同时回复的 CPU/延迟、图片语音峰值、重试与日志增长，并保留原系统和代理资源余量。确认目标设备能独立运行 SnowLuma 与 DSH 后再接第二 QQ；共享 DSH 只是后续有资源证据时的优化方向。

## 验收范围与接入后的验证

已用隔离 worker HTTP 服务和真实 Bridge 测试夹具验证身份、路由、范围、存储与故障路径；这些不替代两套真实 QQ 登录。正式接入后还需在指定测试群核验：

- 两个实际 QQ、WS/HTTP 端点与 token 分别对应，错号或断线时拒绝处理。
- 同群两 bot 的人设、私聊、消息、模型 ID 和费用不串用；甲→乙→甲不改变另一 bot 的上下文。
- 默认不互相唤醒，@、引用、拍一拍、重连与重放不能绕过；重启后过滤集合仍有效。
- 普通账号只能访问获授权 bot/对象，自己的卡片历史不能越权修改他人的卡片。
- 一个 worker 不可用不影响 primary；旧 URL、原模型 ID 和账号登录正常。
- 受控模型调用能分别归属费用；缺失明细与估算范围有说明，不把它当成供应商对账证明。

部署与回退按机器人组件处理，保留一致的 SQLite 与相关状态备份；原代理服务、其端口和配置不参与接入操作。
