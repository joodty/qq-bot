# 转向 QQ Agent：保留哪些成果

2026-10-22，所有者决定以 [QQ Agent](https://github.com/K0nd1us/QQ-agent) 为新底座，开发仓库为 [joodty/QQ-agent](https://github.com/joodty/QQ-agent/tree/codex/group-management)。当前仓库与既有部署继续保留，不删除运行数据或停止现有服务。

## 可复用的成果

| 成果 | 新底座的处理 |
| --- | --- |
| 账号密码、注册、Cookie、会话撤销 | 保留权限模型与验证经验，适配新 HTTP 入口，不能复制生产凭据 |
| QQ 本人身份验证与指定对象授权 | 用于群管理身份、群协作和本人私聊；群号输入本身不能授予管理权 |
| 群聊/私聊统一预算 | 复用每日限额、80% 降频、在途预留、未知费用、幂等和跨日思路，按新模型用量与报价适配 |
| Key 加密、本人配置与禁止静默回退 | 与聊天引擎解耦，平台出资/用户出资走同一功能管道 |
| 人设版本、模板、对象应用及冲突保护 | 上游已有分会话人设，不重复做基础覆盖；适配卡片版本、协作和历史 |
| 会话档案、用量归属与 SQLite | 保留数据与稳定标识，先做迁移映射；DSH ID 不等于新引擎可恢复上下文 |
| 隔离测试、公开检查与跨 AI 交接 | 继续使用，新增能力要覆盖群/私聊、不同付款来源与权限范围 |

## 暂不迁移的方向

- 以每个用户的私人 QQ 为核心的自助托管和容器编排。
- 为每台机器人复制 DSH 与 Bridge 整套服务的部署方式。
- 把平台完整 Agent 链和用户 Key 纯文本链作为两套产品能力继续维护。
- 与新导航重复的管理页面、按需求堆出的身份等级与技术术语。

底层多实例兼容可以保留，普通用户产品主线转为：同一个公共机器人、同一群唯一记录、多人按范围管理、每群一份当前配置与共享预算；本人私聊使用同一能力体系。

## 本次经验

1. 平台角色、资源授权、模型能力和付款来源分别建模，不能因为换了一把 Key 就换成能力缩水的引擎。
2. 新能力必须同时检查群聊和私聊；不要为管理员、普通用户分别复制相同业务。
3. 先验证完整最小闭环与资源容量，再扩大自助入口。能登录第二个 QQ 不代表具备无限量托管能力。
4. 页面控件、后端配置、实际调用和依赖要一起验证，避免只有工具勾选项却缺总开关/素材。
5. 金额展示不等于消费限制；控制必须在所有真实付费尝试之前执行，未知费用不能直接释放。
6. 数据迁移、模型会话延续和供应商缓存分别说明，不能把切回档案承诺为必然省钱。
7. 记录“代码存在、已接主链、已通过夹具、已验证实际环境、已部署”各自状态。

## 实施边界

新仓库先完成上游基线、统一执行上下文、独立预算内核和公开交接。群管理员自助认证、账户体系、供应商与 Key 的统一运行期选择、预算接入所有付费调用及网页入口仍需后续集成。

本轮旧仓库仅更新文档，不复制或迁移生产数据库，不改变既有账号、角色、聊天档案、费用记录、QQ 服务或同机代理。完整计划与经验见新仓库的 `doc/platform/`。
