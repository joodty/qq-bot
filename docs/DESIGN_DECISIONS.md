# 设计决策与被修正的假设

本文件记录“为什么这样做”，代码和当前需求决定“现在具体怎么做”。2026-10-21—22 的演变整理如下。它不是原始聊天记录，也不包含真实用户、服务器或凭据。

## 1. 不同群的人设与上下文是两件事

**背景**：最初担心多个群共用同一人设，会把聊天上下文混在一起。

**核查后的修正**：原实现已经按群/私聊分别维护会话，上下文并未因为全局人设而共享。真正缺少的是每个对象独立的人设选择。

**选择**：使用统一 `group:号码` / `private:号码` 键保存可选覆盖，缺省继承全局。管理员私聊也是私聊，不另造一种对象。

**代价与保护**：更换有效人设时必须撤销旧一代工具权限和排队发言，避免旧上下文在新角色下继续发送。测试覆盖切换期间异步创建、离线队列与角色变化竞态。

## 2. 从“切人设就新建”转为保存可恢复会话

**背景**：只覆盖当前后端 ID 会让 A → B → A 丢失 A 的继续入口。

**选择**：保存人设身份、聊天对象、后端会话标识与当前选择。切回已有身份时恢复旧会话，显式重建才创建新的历史项。

**纠正过度承诺**：保留会话 ID 能延续上下文，也可能减少重建代价，但不保证供应商提示缓存持续存在或一定省钱；历史越长也可能增加输入用量。

**代价**：需要稳定身份、档案状态和并发控制，不把“当前选择”与“所有历史”塞成一个无法区分的值。

## 3. 从分散 JSON 管理状态逐步迁到 SQLite

**背景**：单文件 JSON 简单，但多个关联对象、账号归属、并发保存和预算预留需要原子更新，手写文件表的约束会越来越多。

**选择**：单体部署采用 SQLite，使用事务、严格格式和 CAS；迁移后 SQLite 为权威数据源，原 JSON 作为冻结备份，不回写覆盖新数据。

**保留边界**：当前 26 张表还不是最终领域模型。JSONL 用量、DSH 消息及 `state_documents` 版本化业务文档仍存在。申请流程先用严格版本文档接入，避免为了每个界面临时加表。

**后续方向**：在有迁移方案、备份和兼容测试后，评估统一 Conversation、ChatSession、UsageRecord 和人设版本。公共“目标业务模型”只用于讨论。

## 4. 网页密码登录与内部机器身份分开

**背景**：旧控制台沿用访问令牌，用户容易把管理令牌、Bridge 凭据与模型 token 混淆；刷新和跨设备操作也不方便。

**已否决**：仅输入管理员 QQ 就登录。QQ 号是标识，不是身份证明；任何知道号码的人都会获得权限。

**选择**：账号密码、随机 HttpOnly Cookie、服务端撤销，密码最短 10 字符；新注册固定普通角色和空授权。网页不再接受 URL/localStorage 令牌，混合 Cookie 与机器头不能提权。内部 worker/MCP 凭据继续隔离保存，不分发给普通用户。

**代价**：要保留登录会话、账号限速和密码派生；单纯隐藏输入框不能替代后端鉴权改变。

## 5. 两个平台角色加资源归属，替代“父子用户”或三等级

**背景**：用户有无 Key、有无机器人会组合出多种能力，最初讨论过父子层级和不同等级。

**问题**：把这些条件变成平台角色，会混淆谁付费、谁拥有机器人、谁能修改平台默认值，也容易让保存 Key 变成权限升级。

**选择**：只有 `admin` / `user` 两类平台角色。另用费用配置、机器人所有权和精确 `botId + conversationKey` 委托描述能力。普通账号对自己的机器人可以有完整业务管理能力，仍不能管理平台和其他人的资源。

**代价**：每条接口都必须明确授权范围；不能只在前端藏按钮，也不能只检查“已登录”。

## 6. 支出控制不只做“每日群报表”

**背景**：看到费用并不能阻止继续扣费；只限制群聊也遗漏了私聊和管理员私聊。

**选择**：统一对象预算，默认每日 ¥1；支出加在途预留参与准入，约 80% 时收敛输出和自主参与，达到限额拒绝新调用，按北京时间换日。平台体验另有个人限额与总额，普通用户不能把自己的预算设置变成平台补贴。

**代价**：金额来自模型报告和价格表估算，已经发出的请求无法当成从未发生。不能用清账本恢复额度；未知费用、取消与重复完成都需要保守处理。保留供应商账单与平台估算的区别。

## 7. 用户自带 Key 时不能静默回退到平台 Key

**背景**：自费 Key 失效、被删或余额不足时，自动回退会让用户操作意外消耗平台资金。

**选择**：停止对应自费调用，必须明确选择平台体验才改变费用来源。Key 加密且绑定所有者/配置身份；工作实例只能获取其所有者明确选择的配置，不能借访客的 QQ 私聊声明取走访客 Key。

**代价**：可用性依赖用户修复配置，界面必须说明失效状态，不能把保存成功宣称为余额/权限已验证。

## 8. 一个界面管理多机器人，不等于一个进程随意换 QQ

**背景**：希望用户接入自己的 QQ 并管理群聊；早期界面让用户填写 Bridge 端口和令牌，要求管理员给凭据，体验与权限边界都不清晰。

**选择**：管理入口统一，实例运行和身份独立。普通用户只提交 QQ、名称与本人费用配置，申请本身不授予权限；平台准备实例，本人完成 QQ 扫码，管理员核验实际身份后再建立归属、费用选择并启用。

**已经修正的竞态**：核验期间退出登录、停用账号、删除配置、改变费用来源或转移机器人归属时，旧请求不能继续启用。失败补偿只能撤销本次仍持有的认领，不能停用新所有者的机器人。

**代价**：目前没有自动编排独立 QQ 运行环境。不能把“提交申请”显示为“机器人已接入”。

## 9. 公开结构帮助理解，但不能公开运行数据

**选择**：公共 ER/字段字典从建表源码生成，只提供固定静态路由，不连接真实数据库。当前模型与目标讨论分开展示。

**原因**：账号、机器人 QQ、会话内容、费用、密钥和部署资料都不应为了说明结构被匿名读取。

## 10. 公开 Git 从脱敏起点开始，演变由文档保存

**背景**：原始运行源码快照形成了本地提交历史，其中早期测试沿用了真实群号，开发笔记也包含机器路径。

**选择**：保留原始历史的本机备份，公开主线只从脱敏后的当前源码开始。保留上游归属与许可证，以本文件记录旧假设、修正和原因，今后按任务提交并推送可审阅的增量。

**代价**：公开用户无法访问原始私有提交；不能把旧分支重新合并到公开主线。发布检查必须扫描待推送历史，因为只改最新文件不能清掉祖先提交。[GitHub 的敏感数据处理说明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)解释了历史再次混入与已公开数据难以收回的问题。

## 11. 普通账号按操作组织页面，手机使用四项底部导航

**触发与旧假设**：把体验、自带 Key、托管三种业务方式放在首屏，再同时展示绑定、费用、API、机器人等表单，原本希望用户先理解自己的权限。实际普通账号反馈看不懂；“选择一个视角，查看权限”也容易被理解为身份或权限切换。

**选择**：主页只强调当前下一步；聊天先选机器人及具体对象再设置人设；费用、API、机器人、账号独立进入；帮助先回答如何操作，技术权限图可选展开。电脑六项侧栏，手机四项底部入口，账号和帮助在顶部。模板内容保存与应用到聊天继续分开，避免导航动作改变运行状态。

**兼容与代价**：保留已有后端接口、Cookie、CAS、权限和会话数据，仅重组静态页面及交互。API 归到费用下作为可选项；机器人完整控制台仍独立，暂不将所有高级表单重做。静态页面重复一小部分导航样式，部署无需引入新的共享资源路径；后续可在有构建方案时统一维护。

**验证边界**：使用真实隔离 Bridge/SQLite 和浏览器检验普通账号首次使用、精确聊天、无授权 URL、草稿、费用显式选择、密码及手机交互；真实手机键盘和浏览器差异仍需设备验证。

## 12. 从申请进度接通网页扫码和独立运行环境

**旧假设与缺口**：第 8 项只实现申请、平台关联和核验，把本人扫码放在平台外操作。网页虽然显示“待扫码”，却没有扫码窗口，普通用户无法自己完成接入。仅有多实例注册表不能视作已经支持自助登录 QQ。

**选择**：保留现有申请与版本约束，新增本人专用的开始、检查、刷新、取消接口。平台安装固定运行组件后，由独立登录服务按申请启动 QQ、SnowLuma、DSH 和 Bridge，在网页显示实际 QQ 登录窗口；后台按实际身份核验后建立归属、明确选择本人费用来源并启用。普通账号的平台角色保持不变。

**隔离与兼容**：内部服务只接受回环机器通道，网页只用 Cookie 和申请 ID/版本。只读程序可共用，QQ/DSH/状态目录和机器凭据独立；OS 身份按申请分配且不随名额复用。用户态网络适配现有禁止容器桥接的部署，不修改既有防火墙、转发或代理。新 Bridge 等到其 DSH 初次浏览器凭据有效后再启动，避免冷启动时把缺失凭据缓存为不可用。既有账号、Cookie、角色与会话不迁移或重建。

**重连与限制**：重连使用当前所有者和当前付费配置，沿用原实例；原所有者在转交后不能看扫码图。名额和内存受物理资源限制，等待扫码有时限；已完成扫码的登录状态保留。支持的扫码窗口尺寸与固定 QQ 镜像一致，其他窗口不作为替代图片。QQ 官方机器人 API 属于另一条接入路线，本轮接通现有客户端方式。

**验证**：实际隔离账号/SQLite 和浏览器覆盖权限、并发、弹窗及自动启用；服务器独立环境验证原生二维码和 DSH 就绪。真实新 QQ 的登录仍需本人手机确认，不能把夹具成功当作已登录真实账号。

## 13. 聊天底座转向 QQ Agent，管理能力按通用模块复用

**触发**：独立 QQ 客户端的常驻资源开销使小型服务器不适合无限量开放私人 QQ 托管；完整 DSH 链与 BYOK 纯文本链又让不同费用来源获得不同能力。增加页面和实例数量不能解决这两项问题。

**选择**：新产品在 QQ Agent fork 开发，公共机器人为多个群/私聊提供同一聊天引擎。账号角色、聊天对象授权、模型能力与费用来源分别判断；保留旧账号/授权/预算/人设版本与测试经验，按新引擎适配。上游已有分会话人设，避免重复实现基础功能。

**当前边界**：新底座的独立上下文、预算模块和迁移文档属于开发基础，不代表运行期凭据解析、预算总出口或群管理页面已接通。现有服务继续由本仓库维护，生产数据不在本轮复制或改写。第 8/12 项的托管功能保留既有兼容，不继续作为新产品主线扩张。

**教训**：先确定完整能力矩阵、最小闭环、资源容量和状态验证，再扩大入口；让共用能力承载业务差异，不为每种账号或付费方式维护另一套 AI。

## 追加模板

新增决策时写清：触发场景、当时的假设、实际证据、采用方案、放弃方案与原因、兼容/成本影响、验证方式、哪些仍只是讨论。保留原决策并标注被何种新决策取代，不把旧错误改写成“从来没发生”。
